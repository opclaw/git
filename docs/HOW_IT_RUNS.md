# HOW IT RUNS — как RADAR работает физически, минимальными усилиями

Проверено в этой песочнице 19.10.2026 руками: не «теоретически можно», а «вот что реально отвечает GitHub API».

---

## 0. Короткий ответ

**Сервер не нужен.** Достаточно трёх вещей:

1. **GitHub Actions по cron** — это и есть наш «бэкенд»: каждые 30–60 минут запускает `ingest.py` (бесплатные минуты, ничего не админить, секреты уже есть).
2. **GitHub Pages** — отдаёт `dashboard.html` + `data/leads.json` как статику. Дашборд не «думает», он только рисует то, что посчитал cron.
3. **LLM-шаг внутри того же job'а** (`llm_enrich.py`) — один вызов на репо, с кэшем. Ключ живёт в Actions secrets, в браузере его нет никогда.

Именно так я и собрал прототип в `radar/mvp/`, и он прогнан на живых данных (см. §1). БД и хостинг доплачиваются **только когда появится состояние** — вердикты, SLA-таймеры, назначения (этап 2 в §5).

## 2. Хостинг: что где можно и чего нельзя

| Вариант | Что получает RADAR | Честные ограничения | Вердикт |
|---|---|---|---|
| **GitHub Pages + Actions** | статика-дашборд, cron-инжест, секреты, история лидов в git, 0 ₽ | Pages — **только статика**: никакого серверного кода, никакого секрета в браузере; `*/30` cron на **приватном** репо = ~2160 мин/мес при лимите 2000 → делать `*/60` или публичный репо | **Старт. MVP целиком здесь** |
| **Vercel** (Next.js) | быстрый UI, ISR/`revalidate`, edge-функции как прокси к LLM | Hobby-план — **только некоммерческое использование**; cron на Hobby урезан по частоте; лимит времени функции (порядка 10 с) режет длинные прогоны; исходящие запросы к API GitHub из функции надо кэшировать | Только если UI важнее конвейера и план командный |
| **Cloudflare Pages/Workers + D1 + Cron Triggers** | самый щедрый бесплатный контур: cron любой частоты, D1 (SQLite) для вердиктов, R2 для snapshot'ов, KV для кэша | нужна аккуратность с лимитами CPU на Worker'е; меньше экосистемы для ML; код тот же Python→нужен слой или переписать ingest на TS | **Этап 2**, когда появится состояние и алерты |
| **Supabase / Neon (Postgres)** | настоящая БД: очередь триажа, статусы, SLA-таймеры, history, row-level security, auth для команды | Supabase free suspend'ит проект при неактивности; не нужно, пока лидов ≤ 500/день и вердикты можно писать в JSON | **Этап 2** (вместе с CF или Vercel) |
| свой VPS / Fly.io / Railway | полный контроль, длинные ML-джобы, BigQuery-клиент | 5–15 €/мес + дежурства, обновления, бэкапы = работа, а не «минимальные усилия» | Только когда ML-часть упрётся в лимиты Actions |

**Вывод:** MVP = Pages + Actions. Через 2–3 недели, когда триаж станет ежедневной рутиной, добавляем Postgres (Supabase/Neon) + API, а дашборд переезжает на Vercel/Cloudflare **без переписывания ядра** — ingest остаётся в Actions.

## 3. Архитектура MVP (и где в ней команды)

```
             cron */30..*/60 (GitHub Actions, ubuntu-latest)
                             │
   ┌─────────────────────────┼──────────────────────────────┐
   │                         ▼                              │
   │  1. GET data.gharchive.org/YYYY-MM-DD-HH.json.gz       │  бесплатный поток событий
   │     фильтр WatchEvent → счётчики по репо + по аккаунтам│  (окно ~3 суток, дальше только BigQuery)
   ├─────────────────────────┬──────────────────────────────┤
   │                         ▼                              │
   │  2. GET api.github.com/repos/{o}/{r}  (1 запрос/канд.) │  метаданные: created_at, pushed, license, topics
   ├─────────────────────────┬──────────────────────────────┤
   │                         ▼                              │
   │  3. сигналы → Lead Score (V,N,C,A,F − M − G)            │  детерминированный код = Т1
   ├─────────────────────────┬──────────────────────────────┤
   │                         ▼                              │
   │  4. llm_enrich.py: README → {ps, tags, what, limits,    │  ← вот здесь «нейронка» = Т3
   │     apply[]}, кэш по sha256(README+model+prompt_ver)   │
   ├─────────────────────────┬──────────────────────────────┤
   │                         ▼                              │
   │  5. tools/validate_contracts.py — битый контракт не живёт│  = Т5-правило, зашитое в CI
   └────────────┬────────────────────────────┬──────────────┘
                ▼                            ▼
   git commit data/leads.json      notify.py → Telegram/Slack (порог + анти-шум)
   + data/history/ГГГГ-ММ-ДД-ЧЧ.json
                ▼
   GitHub Pages: dashboard.html (сортировка, фильтры, drawer с чек-листом, кнопки вердикта)
                ▼
   Т2 ставит вердикт → в MVP localStorage → на этапе 2 в Postgres → Т3 делает бриф → Т5 выборочно ломает
```

Плюс отдельный workflow `scorecard.yml`: `ossf/scorecard-action` на репо со статусом adopt/pilot — OpenSSF Scorecard умеет падать алертом прямо в PR, то есть Т2 получает авто-проверку **без своего сервера вообще**.

## 4. Куда именно прикрепить модель (и куда нельзя)

### Можно и полезно (экономит недели ручной работы)

| № | Что делает модель | Когда | Экономия | Цена/риск |
|---|---|---|---|---|
| L1 | **классификация** README+topics → `PS-xx` + теги + домен (заменяет мои 12 строк ключевых слов) | на этапе 4, один раз на репо | триаж −40 % времени | ~1.5k токенов на репо; кэш → повторных вызовов нет |
| L2 | **5 строк «что решает / чем / для кого / чего не хватает»** в карточку лида | там же | −10 мин/репо вручную | тот же вызов, +200 токенов |
| L3 | **Application Brief v0** для Т3: 3 сценария применения, что заменяет, во что встроим | после вердикта adopt/pilot | −0.5 дня на бриф | нужно проверять: модель охотно выдумывает «у нас» |
| L4 | **суммаризация досье** для руководства (недельный Trend Brief из 5 карточек) | раз в неделю, 1 вызов | −2 ч в пятницу | риск гламуризации → обязательные числа из JSON |
| L5 | **adversarial-черновик** для Т5: «найди 5 причин, почему этот репо — пустышка» | по выборке 10/нед | усиливает критику | модель всегда находит «причины» → только как подсказка, не как вердикт |

### Нельзя (и это принципиально)

- ❌ считать звёзды, velocity, ускорение, дедупликацию, скоринг — только детерминированный код; иначе метрики невоспроизводимы и Т5 ставит K1 = 0;
- ❌ выносить вердикт adopt/reject без проверки человеком (модель не запускала код);
- ❌ отвечать на «безопасно ли это» по README (это работа Scorecard + sandbox);
- ❌ ключ в браузере/в `dashboard.html` — только Actions secrets или серверная функция-прокси.

### Чем и где звать модель

| Канал | Как | Плюсы | Минусы |
|---|---|---|---|
| **GitHub Models** (`models.github.ai/inference/chat/completions`, авторизация `secrets.GITHUB_TOKEN`) | тот же job, ничего не заводить | 0 новых аккаунтов и 0 денег на пилоте; список моделей живой — я его дёрнул, HTTP 200 | квоты на репо/организацию; модели ограничены каталогом |
| **Прямой API-провайдер** (OpenAI/Anthropic/Google) + ключ в секретах | `RADAR_MODEL` через `vars` | любой модельный ряд, батч-режим вдвое дешевле | нужен бюджет; для внутреннего использования — ок, для публичного — следить за ToS |
| **Локально: Ollama/vLLM** на своём железе или VPS 5–10 € | invoke из того же скрипта | данные не уходят, нет per-token | качество маленьких моделей ниже на классификации; надо держать аптайм |
| **Embeddings** (эти же API или локальная `multilingual-e5`) | один раз за жизнь репозитория на sha README | дешёво (копейки/мес), даёт novelty и кластеры | хранить вектора: в MVP — SQLite, дальше pgvector |

Практика из прототипа: `llm_enrich.py` выбирает провайдер по наличию ключа (сначала `OPENAI_API_KEY`, иначе бесплатный `GITHUB_TOKEN`), молча пропускает шаг без ключа и **кэширует в `.llm_cache` по sha256(README + model + prompt_version)** — то есть повторный cron по тому же репо стоит 0 токенов.

Оценка расхода на реалистичный поток: 400 новых репо/день × ~2k токенов вход + 0.4k выход ≈ 1M токенов/день на дешёвом модельном классе (mini/flash) ≈ **единицы долларов в месяц** (а с кэшем по sha — в 3–5 раз меньше, потому что большинство репо переклассифицировать не надо).

## 5. Куда девать состояние (вердикты, назначения, SLA) — по этапам

| Этап | Хранилище | Что становится возможным | Триггер перехода |
|---|---|---|---|
| **0 · MVP** (сейчас) | `leads.json` в git + localStorage браузера | очередь, объяснения скора, черновик вердикта, полная история изменений в `git log` | — |
| **1 · git-native** | тот же репо, файл `triage/ГГГМММ.json` + PR на каждый вердикт | ревью вердиктов, blame, «журнал решений» = diff, veto Т5 как required check | когда вердиктов >20/день и их кто-то пересматривает |
| **2 · Postgres** | Supabase/Neon: `leads`, `verdicts`, `sla_timer`, `users`; дашборд на Vercel/CF + API | настоящие назначения, SLA-таймер с авто-эскалацией, метрики p90, параллельные аудиторы, алерты на просрочку | когда появится требование «p90 ≤4 ч измерять, а не помнить» |
| **3 · очереди + ML** | + Redis/Queues, ClickHouse/DuckDB поверх истории, обученный ранжировщик | LambdaMART на golden set, анти-гейминг-граф, real-time на хайп-пики | когда Precision@Top50 упрётся в ручные веса |

Переход 0→1 — это `git mv`, 1→2 — одна таблица и один CRUD. Ядро (ingest + скоринг) не переписывается ни разу: контракт `radar/leads.v1` уже валидируется кодом.

## 6. Экономика и лимиты (то, что ломает «бесплатно», если не посчитать)

| Ресурс | Нагрузка MVP | Бесплатный лимит | Итог |
|---|---|---|---|
| GH Archive | 4 файла/прогон × 9 МБ; при 48 прогонах/сут ≈ **1.7 ГБ/сут** входящего трафика | Actions egress внутрь GitHub — бесплатно | ✅ 0 ₽ |
| GitHub API | **1 вызов на прогон** после прогрева кэша (было 40) | authenticated 5000/час; без токена 60/час | ✅ 0 ₽; упор в квоту лечится батчем через Search + `data/cache.json` — проверено в бою |
| Actions минуты | прогон ≈ 1.5 мин → 48 × 1.5 = **72 мин/сут = 2160/мес** | public — безлимит «разумно»; private Free — 2000 мин/мес | ⚠️ **на приватном репо `*/30` не влезает** → `*/60` (≈1080 мин/мес) либо публичный репо |
| LLM | ≈1M токенов/сут с кэшем | GitHub Models — квоты токена задачи | ✅ 0 ₽ на пилоте, $3–10/мес на прямом API |
| Pages | статика 28 КБ + JSON | 1 ГБ, 100 ГБ/мес трафика | ✅ 0 ₽ |
| Postgres (этап 2) | ~50k строк/мес | Supabase 500 МБ, Neon 0.5 ГБ | ✅ 0 ₽, при росте 25 €/мес |

**Итого пилот: 0 ₽/мес и один репозиторий.** Цена «качественно» — не деньги, а дисциплина: cron не должен молчать при пустом окне (у нас это WARN в валидаторе), а LLM-шаг не должен блокировать выдачу (у него `exit 0` без ключа).

## 7. Что команды физически делают в этом дашборде

- **Т1** меняет формулу — commit в `ingest.py`; CI прогоняет бэктест; без таблицы абляции ревью не открывается (правило Т5).
- **Т2** открывает drawer, видит `score_explain` + 4 чек-бокса, жмёт `adopt/pilot/watch/reject` + обязан оставить обоснование. Время фиксируется автоматически → метрика «triage p90 ≤15 мин» считается из данных, а не по ощущениям.
- **Т3** забирает `fit/PS` и `llm.apply[]` в бриф; бриф — markdown в том же репо, чтобы «куда применить» было в diff, а не в голове.
- **Т4** следит за одним: cron прошёл, контракт валиден, Pages отдает, алерт не молчит.
- **Т5** каждую пятницу: (а) пересчитывает метрики своим скриптом, (б) делает вбросы в тестовое окно, (в) ставит K1–K10. Rubric-оценки — тот же JSON, что читает дашборд, поэтому спорить можно про число, а не про впечатление.

## 8. Чего в MVP сознательно нет (и что это стоит)

| Не сделано | Чем грозит | Когда закрываем |
|---|---|---|
| Таймлайн звёзд по `starred_at` (требует токен/GraphQL — REST `/stargazers` без токена 401) | окно ≤6 ч, «история» не восстанавливается задним числом | S1, SRC-02 через GraphQL `stargazers(orderBy: STARGAZERS)` |
| BigQuery/GH Archive backfill (у архива хранятся только последние ~3 суток) | накопление истории начинается с дня запуска, а не с нуля | S0 — запустить cron **в первый же день**, иначе месяц потерян |
| Настоящий анти-гейминг (граф аккаунтов: возраст, followers, кольца) | M = грубый proxy (доля «колец» и само-звёзд) | S1, ANTI-01 |
| Golden set + Recall/Precision | **нельзя утверждать, что мы раньше Trending** — только что мы вообще находим | S2, EVAL-01…03 |
| Дедуп по форкам/rename | 1 событие = 2 лида на форки-штамповки | S1, INF-04 |
| Sandbox-проверка и Scorecard в досье | «репро-не-проверенные» claim'ы проходят | S2, TRI-03 |
| Учёт токенов и лимитов при 500+ репо/сут | Actions будет жевать минуты | этап 2 |

Это ровно те пункты, которые стоят в бэклоге первыми. Прототип доказывает только одно: **конвейер реален и бесплатный**. Утверждение «мы ловим раньше» требует golden set — без него это вера, а не метрика.

## 9. Как это развернуть (реально на вечер, а не на квартал)

```bash
# 0. из папки radar/ собрать готовый репозиторий (deploy/ со всеми файлами на местах)
python3 tools/ship.py && cd deploy

# 1. проверить локально ровно то, что сделает CI (~20 секунд, квоту почти не тратит)
python3 mvp/ingest.py --hours 8 --top 24
python3 mvp/build_dashboard.py && cp dashboard.html index.html
python3 tools/validate_contracts.py data/leads.json

# 2. создать публичный репозиторий и толкнуть (публичный = минуты Actions без лимита 2000/мес)
git init -q && git add -A && git commit -qm "radar: MVP"
gh repo create radar --public --source=. --push

# 3. включить статику: Settings -> Pages -> Source: GitHub Actions
#    и Settings -> Actions -> General -> Workflow permissions: Read and write

# 4. первый прогон вручную, дальше cron сам:  gh workflow run radar-ingest
#    сайт: https://<user>.github.io/radar/index.html

# 5. LLM бесплатно по токену задачи (GitHub Models) - отдельной настройки не требует;
#    заменить модель: gh variable set RADAR_MODEL --body openai/gpt-4.1-mini

```

Время на «чтобы оно само крутилось»: 1–2 часа. Время на «качественно и по плану»: спринты S0–S1, где к этому ядру добавляются backfill, GraphQL-обогащение, граф накрутки и golden set. Ядро при этом не переписывается — оно у нас уже есть и работает.
