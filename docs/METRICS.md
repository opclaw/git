## 1. Формула Lead Score (версия v0 → целевая v1)

```
L = 0.30·V + 0.20·N + 0.10·C + 0.10·A + 0.30·F  − 0.40·M − 0.25·G      (v0, ручные веса)

V  = velocity   : robust-z от (Δstars_7d / Δstars_expected(возраст, размер))
                  + 0.3·z(Δforks) + 0.2·z(новые контрибьюторы) + 0.2·z(релизы)
N  = novelty    : 1 − max cosine-сходства эмбеддинга README с кластерами известной кодовой базы
                  (штраф за d-й репо того же кластера: N ×= 1/log2(2+d))
C  = community  : bus factor, медиана ответа на issues, open_issue_ratio, CODEOWNERS, CI, DCO
A  = actor trust: возраст/качество starred-аккаунтов, verified org, связанные аккаунты
                  (fork-network с известными людьми), presence в 2+ внешних источниках
F  = fit        : match к онтологии problem statements Т3 (0..1)
M  = manipulation risk (0..1 из anti-gaming модели)   → вычитается
G  = stagnation/decline (0..1: коммитов нет, issue не отвечены, README устарел) → вычитается
Жёсткие отсечки: нет LICENSE → вердикт reject без досье;  license-incompatible → не выше watch.
```

v1 (S3): веса обучаются логистической регрессией на golden set, затем LambdaMART. Любая смена весов требует **таблицу абляции + стабильность по фолдам** (иначе Т5 ставит K3 = 1).

## 2. Как считается «рано» (главная метрика продукта)

```
lead_days(repo) = date(GitHub Trending first appearance) − date(our first_seen)
Lead time advantage = median over repos в golden set с lead_days > 0
Ранний перехват = доля репо, помеченных нами при stars < 500 ИЛИ ≤ 30 дней от перегиба
```

Перегиб (inflection point) `t*`: дата, после которой 7-дневный rolling-наклон log(stars) превышает p90 собственного исторического распределения репо. Точка считается **только по данным до t** — иначе это hindsight bias.

Пороги: приёмка ≥ 7 дней в медиане, цель ≥ 14. Отдельно публикуем **медиану и p75**: если p75 < 0 — мы в среднем опаздываем, и это надо писать прямо.

## 3. Метрики качества (всё на golden set, temporal cut)

| Метрика | Определение | Приёмка | Цель |
|---|---|---|---|
| Recall@30d | доля «стоило взять» репо, помеченных в течение 30 дней после t* | ≥ 50 % | ≥ 65 % |
| Precision@Top50 (нед.) | доля принятых Т2 в статус `adopt/pilot` в нашем недельном Top-50 | ≥ 35 % | ≥ 50 % |
| Top-noise rate | доля репо, отклонённых Т2 как «мусор/накрутка», в наших дайджестах | ≤ 20 % | ≤ 10 % |
| Time-to-verdict p90 | first_seen → вердикт | ≤ 6 ч | ≤ 4 ч |
| Triage p90 | время 15-минутного чек-листа | ≤ 15 мин | ≤ 10 мин |
| Anti-gaming catch | отбито из 10 вброшенных сценариев | ≥ 7 | ≥ 9 |
| Adoption | внедрённых в прод инструментов за квартал | ≥ 2 | ≥ 4 |
| Measured value | эффекты с подтверждённой цифрой (час/нед или деньги) | ≥ 1 | ≥ 3 |
| Cost per lead | расход инфраструктуры / число лидов | ≤ $0.05 | ≤ $0.02 |
| Coverage gaps | часы без данных ingest за месяц | ≤ 8 ч | ≤ 2 ч |
| Post-adopt incidents | CVE/заброшенность у adopted-репо за 90 дней | 0 | 0 |

### 3.1 Golden set — как его не подделать

- 200 репо: 100 «положительных» (после t* их реально стоило взять — выжили, 500+ звёзд/квартал, 2+ год поддержки, 3+ внешних упоминания), 100 «отрицательных» (хайп без продолжения, накрутка, клон, мёртвый).
- **Правило отсечки:** все признаки считаются только по снимкам ≤ t*. Любой доступ к данным позже t* = утечка = находка S1.
- Разметка независимая: 2 оценщика, расхождение → третий. Требуем **Cohen κ ≥ 0.6**; иначе датасет не годится как судья.
- Датасет заморожен (sha256 в репо). Т1 не имеет права менять состав между прогонами; запрос на ротацию 20% состава — раз в квартал, через RFC и визу Т5.
- Отчёт по сегментам: язык (py/js/rust/go), домен (AI/инфра/devtools/безопасность/данные), возраст репо, «новое vs возрождённое». Мы обязаны показать, где проигрываем.

### 3.2 Как не считать успехом собственную имитацию

Т5 пересчитывает Recall/Precision/lead time **своим** скриптом на `raw_snapshot_uri`. Расхождение с цифрами команды → K1 = 0. Дополнительно каждую неделю рандомные 10 одобренных репо прогоняются «вслепую» (второй аудитор без доступа к скорингу) — совпадение вердиктов отслеживается как метрика честности процесса.

## 5. Правила приоритизации (чтобы P0 не значило «всё»)

- **P0** = без этого gate не проходит (30 задач). **P1** = нужно для цели квартала (33). **P2** = улучшает, но система работает и без этого (8).
- Ресурсный конфликт решается по порядку: `закрыть находку S1/S2 с истёкшим сроком` → `SLA конвейера` → `качество метрик` → `новые источники` → `UX` → `всё остальное`.
- Правило «выбросить без слёз»: при перегрузе >100 % команды из её спринта удаляются сначала P2, потом задачи с наибольшим отношением оценка/вклад в gate. Решение публикуется в decision log (ORG-03).
- Новая идея = RFC + вычеркнутая старая задача. Приём «и вот это добавим» запрещён.
